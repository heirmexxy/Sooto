# Open Financial Proof (OFP) — Specification v0.1 (draft)

**Status:** Working draft, published with its reference implementation (Sooto). Comments welcome as GitHub issues.
**Licence:** This specification may be implemented by anyone, royalty-free.

## 1. Purpose

A person or business often has to prove something about their money to someone else: a lender, a landlord, a university, an employer, a consulate. Today they hand over whole bank statements. That exposes far more than the question needs, and statements are easy to forge and impossible for most verifiers to check.

An **Open Financial Proof** answers one narrow question ("did this account hold at least ₦3,000,000 for 28 consecutive days?") for **one named verifier** and **one purpose**. It is signed by an issuer the verifier can identify, so it cannot be altered. It reveals the answer, not the transactions behind it.

OFP is vendor-neutral. Any bank, aggregator, fintech or open-source server can issue proofs. Any verifier can check them with a public key and the steps in §7.

## 2. Roles

| Role | Who | Does what |
|---|---|---|
| **Subject** | The person or business the proof is about | Asks for a proof and chooses who receives it |
| **Issuer** | Software or institution that computes and signs the proof | Reads the subject's data with consent, computes claims, signs |
| **Verifier** | Whoever receives the proof | Checks signature, expiry, addressee and trust level, then decides |
| **Source** | Where the data came from | A statement, a live account connection, or the institution itself |

## 3. Principles

1. **Minimal disclosure.** Answer the verifier's question with yes/no and coarse bands. Exact figures only when the subject explicitly chooses to include them.
2. **One verifier, one purpose.** Every proof names its verifier and purpose. A verifier rejects a proof addressed to someone else.
3. **Honest risk signals.** Signals a verifier would reasonably want, such as large deposits shortly before the window ends, are always included. Issuers must not offer a way to suppress them.
4. **Deterministic claims.** Claims are computed by deterministic code from the source data. They are never generated by a language model.
5. **Short lives.** Proofs expire. The default lifetime is 30 days, and the maximum is 90.
6. **Visible trust.** Every proof states how far its source can be trusted (§4).
7. **No data trade.** An issuer must not sell or reuse a subject's data beyond issuing the proofs the subject asked for.

## 4. Trust levels

| Level | Source | What the issuer can vouch for |
|---|---|---|
| **L1** | A document the subject supplied, such as a statement export | It is internally consistent: running balance, totals, dates. It is **not** a guarantee that the institution produced it. |
| **L2** | Read live from the institution over an authenticated, consented connection (open-banking API, aggregator) | The institution reported this data at that time. |
| **L3** | Signed by the institution itself, e.g. a bank co-signing the proof | The institution vouches for it. |

Verifiers set the minimum level they accept. An issuer must not issue an L1 proof from a statement that failed consistency checks.

## 5. Envelope

A signed proof is a JSON object:

```json
{
  "proof": {
    "ofp": "0.1",
    "id": "6f1c…",
    "type": "funds_held",
    "issuer": "https://sooto.example.org",
    "verifier": "University of Leeds admissions",
    "purpose": "CAS financial evidence",
    "subject": { "declared_name": "Ada Obi", "name_verified": false },
    "trust_level": "L1",
    "source": {
      "provider": "statement",
      "digest": "sha256:9b2e…",
      "verification": "consistent",
      "period": { "from": "2026-06-01", "to": "2026-09-26" }
    },
    "claims": { "…": "see §8" },
    "nonce": "optional, from the verifier",
    "issued_at": 1795000000,
    "expires_at": 1797592000
  },
  "signature": "base64url Ed25519 signature",
  "key_id": "short id of the signing key",
  "alg": "Ed25519"
}
```

| Field | Required | Meaning |
|---|---|---|
| `ofp` | yes | Specification version. Verifiers reject versions they do not know. |
| `id` | yes | Unique id of this proof. |
| `type` | yes | The template (§8). |
| `issuer` | yes | URL of the issuer. Its issuer document is at `{issuer}/.well-known/ofp-issuer`. |
| `verifier` | yes | Who the proof is for. |
| `purpose` | yes | What it is for. |
| `subject` | no | Declared identity. `name_verified` is true only when the issuer checked the name against an identity source. |
| `trust_level` | yes | L1, L2 or L3 (§4). |
| `source` | yes | Provider, a digest of the source data, the verification result for L1, and the period covered. |
| `claims` | yes | Template-specific (§8). |
| `nonce` | no | A value the verifier supplied, to bind the proof to its request. |
| `issued_at`, `expires_at` | yes | Unix seconds. |

## 6. Canonical form and signature

The signature covers the **canonical JSON** of the `proof` object:

- object members sorted by key (Unicode code point order) at every depth;
- no insignificant whitespace;
- members whose value is undefined are omitted;
- strings and numbers serialised as in ECMAScript `JSON.stringify`.

This matches RFC 8785 (JCS) for the value types a proof contains. The signature is Ed25519 over the UTF-8 bytes of that string, encoded base64url without padding.

## 7. Verification (what every verifier must do)

1. Fetch `{issuer}/.well-known/ofp-issuer` over HTTPS and find the key whose `key_id` matches.
2. Check that `ofp` is a version you support and `alg` is `Ed25519`.
3. Verify the signature over the canonical form of `proof` (§6).
4. Check that `expires_at` is in the future and `issued_at` is not in the future, allowing 60 seconds of clock skew.
5. Check that `verifier` is you, and that `nonce` matches if you supplied one.
6. Check that `trust_level` meets your minimum, and reject if `source.verification` is `inconsistent`.
7. Read `claims`, including any `risk_signals`, and decide.

Issuer document:

```json
{
  "ofp": "0.1",
  "issuer": "https://sooto.example.org",
  "keys": [{ "key_id": "…", "alg": "Ed25519", "public_key": "base64url SPKI DER" }],
  "trust_levels_issued": ["L1"]
}
```

## 8. Templates

### 8.1 `funds_held` (proof of funds)

The question: did the account hold at least `amount` at the end of each of `days` consecutive days ending on `window.to`? Uses include student and work visas (for example, the UK's 28-day rule), tenancy deposits and supplier checks.

| Claim | Meaning |
|---|---|
| `question` | The question in words |
| `held` | true / false |
| `amount`, `currency`, `days` | The threshold asked about |
| `window` | `{from, to}` |
| `lowest_balance_band` | Band containing the lowest end-of-day balance in the window |
| `transactions_in_window` | Count |
| `risk_signals` | e.g. `late_large_credit`, `in_and_out` |
| `fx` | When the threshold currency differs: `{from, to, rate, source, date}` |
| `exact` | Only if the subject chose to disclose: `{lowest_balance}` |

End-of-day balances carry forward over days without transactions.

### 8.2 `cashflow` (income regularity)

Uses include lending, tenancy, employment and supplier credit.

| Claim | Meaning |
|---|---|
| `period`, `months_covered`, `active_months` | Coverage |
| `avg_monthly_inflow_band` | Band |
| `inflow_consistency` | `high` (variation ≤ 0.25), `medium` (≤ 0.6), `low`, or `insufficient_data` |
| `distinct_payers_band` | `1`, `2-4` or `5+` |
| `top_payer_share_band` | `under 50%`, `50-80%` or `80%+` |
| `min_avg_monthly_inflow`, `meets_min_avg_monthly_inflow` | When the verifier set a threshold |
| `exact` | Only if the subject chose to disclose |

### 8.3 Reserved for future versions

`income` (employer-matched salary), `tenancy` (rent-to-income and on-time rent history), `business_health` (revenue band, months trading, customer concentration) and `means_test` (income below a threshold).

## 9. Risk signals

| Signal | Definition (v0.1) |
|---|---|
| `late_large_credit` | A credit in the last 30 days of the data, at least 5× the median credit and at least 40% of the closing balance |
| `in_and_out` | A credit at least 3× the median credit, followed within 7 days by debits totalling at least 80% of it |

## 10. Security considerations

- **Injection.** Narrations and counterparty names are written by third parties. Issuers must treat them as data, must never let them influence whether or what a proof says, and should flag instruction-shaped text.
- **Probing.** A party able to request many yes/no proofs at different thresholds could binary-search a balance. Issuers should only issue proofs the subject asks for, and should rate-limit.
- **Replay.** Verifiers that need freshness should supply a `nonce`.
- **Key compromise.** Issuers rotate keys by publishing the new key alongside the old one until all proofs signed with the old key have expired.

## 11. Alignment and roadmap

- v0.2: express proofs as W3C Verifiable Credentials 2.0 / SD-JWT VC, presentable through OpenID4VP and the EU Digital Identity Wallet as electronic attestations of attributes.
- v0.2: L2 sources (open-banking aggregators, Nigeria's NIBSS open-banking registry), and L3 co-signing by institutions.
- Conformance test suite, so any implementation can show it follows this specification.
- Governance: move the specification to a neutral foundation once three or more independent implementations exist.
